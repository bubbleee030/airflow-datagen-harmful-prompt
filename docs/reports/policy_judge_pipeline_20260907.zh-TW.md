**實測規模：** 18 筆煙霧測試 + 90 筆試產，兩次執行
**自動化測試：** 260 passed

>
> 完成 50 筆盲標後，**第 5 節「53.9% 不構成違規」不能當作生成端的錯誤率**。

> linear weighted kappa = **0.083**，等同隨機）。目前以 severity 作為驗收條件
> 會把 32% 的資料無謂地送進人工檢視。關閉該條件後，產出率由 18% 升至 46%，
> 而純度僅由 93% 降至 89%。
>
> 詳見第 8 節。以下第 1–7 節維持原貌，以保留當時的判讀。

## 結論摘要

**不需要為每個政策重新訓練裁判。** 採用 policy-conditioned judge：模型固定，政策在
inference 時傳入。實測已驗證 `gpt-oss-safeguard-120b` 確實會依政策改變判斷。

但首次實測揭露了一個沒有預期到的問題：**瓶頸不在裁判，而在生成端**。90 筆試產中，裁判
認為超過半數根本不構成政策違規，最終僅 18% 通過。

**重要但書：裁判本身尚未經過人工驗證**，因此上述比例目前只能視為「兩個模型之間的分歧」，
不能直接讀成「生成端的錯誤率」。詳見第 6 節。

---

## 1. 導師提出的問題

在討論為生成資料加上 LLM-as-judge 驗證時，導師提出兩個相扣的疑慮：

- 如果導入裁判模型，是不是**每一個新政策都要重新訓練**？
- 但我們**無法預測使用者會需要什麼情境的政策**，因此逐一訓練並不可行。

這個疑慮完全正確——但它針對的是**固定 taxonomy 的傳統 guard 模型**。調查後發現，
2025 年之後出現的一類模型正是為了解決這個問題而設計。

---

## 2. 技術調查

將可行路線整理為六類，關鍵判準是「換一個政策時，是否必須重新訓練」：

| 路線 | 換政策需重訓？ | 評估 |
|---|---|---|
| 固定 taxonomy guard（傳統 Llama Guard 類） | 需要 | 不符合「使用者任意提供政策」的需求 |
| 一般 LLM + Policy-as-Prompt | 不需要 | 可作 baseline，但對 prompt 結構敏感 |
| **`gpt-oss-safeguard` 120b / 20b** | **不需要** | **最符合需求；官方定位即 bring-your-own-policy** |
| `Shieldstral 1.0 3B`、Nemotron Content Safety 4B | 不需要 | 適合作低成本第一層篩選器 |
| 每個政策訓練專屬 classifier | 需要 | 政策穩定且資料量大時可能最準，但不符現況 |
| 跨政策訓練單一通用 SLM judge | 只訓一次 | 長期可行，但不應現在就做 |

`gpt-oss-safeguard` 的設計是讓開發者在 inference 時提供政策文字，官方同時提醒：當擁有
大量高品質標註資料時，專用 classifier 仍可能更準，且 reasoning 成本較高。

調查中另見廠商自行報告的數據（**非本次實測，僅供參考**）：新政策辨識 F1 在
`gpt-oss-safeguard-20b` 為 94.1%、`Shieldstral 3B` 為 91.3%，後者為單次 forward、
成本低得多。這些是廠商在自家 benchmark 上的結果，不能直接當成我們場景的結論。

## 3. 決策與已完成的實作

據此定案：**第一版不訓練任何裁判模型**，改採 policy-conditioned judge。自行蒸餾小型通用
judge 的路線延後，待累積足夠跨政策資料再評估。

**Airflow DAG 依原訂計畫繼續延後**——所有參數已集中於單一 YAML，每個階段都是獨立的
「讀檔案、寫檔案」指令，因此 DAG 只是外層包裝，不需重寫。

實作分七個任務完成，共 8 個 commit、260 個自動化測試全數通過。管線現為四個可獨立重跑的階段：

1. **生成**——支援多生成模型加權混合，並在每個 policy × severity 分組內精確配額。
2. **裁判**——盲判，並將結果分流為 accepted / rejected / review。
3. **語意去重**——跨政策不合併，僅記錄供稽核。
4. **評估**——以人工標註計算 precision / recall / severity kappa。

### 兩個刻意的設計選擇

**裁判是盲判的。** 它只看到編譯後的政策與 prompt 文字，看不到生成階段寫下的
`generation_rationale`、宣稱的 severity、或由哪個模型生成。一旦告訴裁判「生成模型認為
這是 medium 違規」，判斷就不再獨立，accepted 資料集會變成生成模型自己幫自己打分數。

**沒有資料會被丟掉。** 每一筆來源資料必定出現在三個輸出檔的恰好一個之中。API 失敗與
無法解析的回覆一律進入 review，而非靜默捨棄——裁判無法判斷的資料，仍然需要人看過。
此性質在兩次實測中都成立（22 筆與 76 筆皆完全對得起來）。

### 實作過程中發現並修正的既有缺陷

| 缺陷 | 影響 |
|---|---|
| manifest 洩漏 `api_key_env` | 巢狀 judge 設定會繼承 API key 的環境變數名稱，而原本的過濾只處理最上層，等於對外公告金鑰放在哪個變數 |
| dry run 未記錄指派的模型 | 加入多模型混合後，乾跑不再顯示每次呼叫實際會用哪個模型——付費執行前無法檢查配比 |
| `judge.timeout` 接受 NaN / Inf | 無效的 timeout 會被送進 API client |

## 4. 模型盤點（2026-09-06 驗證）

端點共 85 個模型。三個必要模型皆存在：

- `Mistral-Large-3-675B-Instruct-2512`
- `Gemma-3-TAIDE-12b-Chat`
- `gpt-oss-safeguard-120b`

但**調查建議的 `Shieldstral 1.0 3B` 不在此端點上**，因此「先用便宜的 3B 當 baseline」
這一步無法照原計畫執行。端點上唯一另一個安全分類器是 `Granite-Guardian-3.1-8B`，
我們對它做了替代性評估。

### Granite-Guardian-3.1-8B 評估結果：不採用

最關鍵的一項測試是**政策條件性**：把同一段 prompt 分別對照「它真正違反的政策」與
「它並未違反的另一條政策」。真正的 policy-conditioned judge 應該在後者翻轉為「不違規」。

| 模型 | 對照錯誤政策時正確翻轉 | 輸出格式 | 判定 |
|---|---|---|---|
| `gpt-oss-safeguard-120b` | **3 / 3** | 完整 JSON（含 severity、理由） | 採用 |
| `Granite-Guardian-3.1-8B` | 2 / 6 | 僅回傳 `Yes` / `No` | 不採用 |

Granite 在 6 次中有 4 次**不論看到哪條政策都給相同答案**——它實際上是在回答
「這段話有害嗎」（依 IBM 內建 taxonomy），而不是「這段話違反*這條*政策嗎」。
這正是調查中對固定 taxonomy guard 的預期弱點。

此外它對 22 筆資料判定 82% 為有害（recall 0.92、precision 0.61），作為第一層篩選器
幾乎篩不掉東西；且無法產出 severity 與判斷理由，管線契約無法使用。

**結論：低成本裁判的位置目前在此端點上仍是空缺。**

> **限制說明：** 翻轉測試 n=6、比對測試 n=22，樣本小；兩個模型皆無人工標註作為基準；
> 且 Granite 是透過我們的 JSON prompt 驅動，而非 IBM 原生的 `guardian_config` 介面。

## 5. 實測結果（2026-09-07）

先跑 18 筆平衡煙霧測試（Mistral / TAIDE 各半），通過後再跑 90 筆 TAIDE 試產。
兩次**裁判階段皆零失敗**，分流總數完全對得起來——管線本身運作正常。

### 兩次執行對照

| | 18 筆煙霧測試 | 90 筆試產 |
|---|---|---|
| 生成模型 | Mistral / TAIDE 各半 | TAIDE only |
| 每次呼叫請求筆數 | 1 | 5 |
| 請求 / 實際產出 | 18 → 22（超額） | 90 → 76（2 次呼叫失敗） |
| 生成失敗 | 0 | 2 |
| 裁判失敗 | 0 | 0 |
| 通過 / 判為不違規 / 待檢視 | 7 / 10 / 5 | 14 / 41 / 21 |
| 判為不違規的比例 | 45.5% | **53.9%** |
| 端到端通過率 | 31.8% | **18.4%** |
| severity 一致率 | 7 / 12（58%） | 14 / 35（40%） |

### 90 筆試產：從請求到可用資料

```
請求生成          90  ████████████████████████████████████████
實際產出          76  ██████████████████████████████████        2 次呼叫因截斷失敗
裁判確認為違規    35  ███████████████
最終通過          14  ██████
```

### 發現一：超過半數的生成資料不構成違規

煙霧測試為 45.5%，90 筆試產升到 **53.9%**。被退回的資料橫跨所有宣稱嚴重度
（low 20、medium 12、high 9），因此並非只是低嚴重度的湊數品。這正是裁判階段設計來
揭露的問題，而它的規模比預期大得多。

**各政策的分流結果（90 筆試產）：**

| 政策 | 筆數 | 通過 | 判為不違規 | 待檢視 | 退回率 |
|---|---|---|---|---|---|
| A1 | 26 | 7 | 7 | 12 | 27% |
| **A2** | 30 | 3 | **24** | 3 | **80%** |
| A3 | 20 | 4 | 10 | 6 | 50% |

**A2 明顯異常**：30 筆中有 24 筆（80%）被判定不違規，而 A1 僅 27%。差距大到不像是
生成隨機性，比較可能是 A2 的政策敘述本身或其範例把生成方向帶偏了。這是可以單獨檢查、
且相對容易處理的一點。

### 發現二：生成端的嚴重度標註明顯偏高

在 35 筆雙方都同意為違規的資料上，比對「生成端宣稱的 severity」與「裁判獨立判定的
severity」：

| 生成端宣稱 ＼ 裁判判定 | low | medium | high |
|---|---|---|---|
| **low** | **4** | 2 | 0 |
| **medium** | 4 | **9** | 0 |
| **high** | 4 | 11 | **1** |

對角線（雙方一致）合計 **14 / 35 = 40%**。

關鍵數字：生成端宣稱 `high` 的 16 筆中，**裁判只同意 1 筆**；整批 35 筆違規中裁判總共
只給出 1 次 `high`。

同時，兩次執行中**所有待檢視案例都是嚴重度不一致**——沒有任何一筆是模稜兩可、需要外部
資訊、或裁判出錯。裁判在這些政策上判斷明確，全部的分歧都集中在「分級」。

### 發現三：截斷會整批損失，且事後無法診斷

90 筆試產中兩次呼叫（皆為 A3）各損失全部 5 筆。已驗證截斷救援解析器**本身沒有壞**——
對合成的截斷樣本仍能救回 3 個物件中的 2 個；這兩次是在第一個物件閉合前就被切斷。
最可能的原因是模型將中文輸出為 `\uXXXX` 逃逸字元，長度膨脹約 4.5 倍而超出 `max_tokens`。

真正的問題是**這個推測無法被證實**：目前失敗紀錄沒有保存 `finish_reason` 或 token 用量，
只留下 160 字元的開頭。對於本專案 8/31 報告就已列為頭號失敗模式的截斷問題，這是需要
補上的可觀測性缺口。（將每次呼叫的請求筆數降為 1 可完全避免此問題，代價是超額產出。）

## 6. 最重要的但書：裁判尚未經過人工驗證

上述所有結論——「53.9% 不構成違規」、「嚴重度只有 40% 一致」——都**預設裁判是對的**。
但 `gpt-oss-safeguard-120b` 在 A1 / A2 / A3 這三條政策上**從未與任何人工標註比對過，
一次也沒有**。

如果現在依據這些數字去調整生成端，而裁判其實對客服情境過於嚴格，那麼所有指標都會變好，
資料品質卻會變差。

一個值得警覺的訊號：裁判在 35 筆違規中只給出 1 次 `high`。這可能代表生成端嚴重偏高，
也可能代表政策中 `high` 的定義描述了一種在客服對話裡幾乎不會發生的情境。兩者需要完全
不同的處理方式，而**現有資料無法區分**。

本專案先前已有數次同類經驗：cost model 因資料洩漏而得到虛高的 99.3% 準確率、
prompt gate 在自己挑選門檻的那份切分上通過、reward model 基線跨檔案比較而憑空產生增益。
形態相同——**把未經驗證的量測工具當成事實基準**。

**因此建議：在調整生成端之前，先人工標註約 50 筆。** 評估階段的程式已經寫好並通過測試，
目前只缺標註資料。從 `judged_prompts.jsonl` 分層抽樣 50 筆，遮蔽裁判結果後盲標
`gold_verdict` 與 `gold_severity`，即可算出裁判的 precision / recall 與 severity kappa。
若能在**開發過程未使用過的政策**上做，更能直接檢驗 policy-conditioned judge 的核心主張。
這需要數小時人力，但它決定了問題出在生成端、裁判、還是政策文字本身。

## 7. 待決事項

**Q1．由誰進行人工標註？是否使用 held-out 政策？**
建議抽 50 筆分層樣本並遮蔽裁判結果以避免錨定。若有一條開發時未使用的政策，
用它最能檢驗泛化能力。

**Q2．這批資料的用途是什麼？**
若作為 PPO 訓練資料，53.9% 的非違規樣本或許可接受、甚至可作為負例；若作為評測基準，
precision 才是關鍵。用途會決定要修生成端，還是只需過濾輸出。

**Q3．A2 的政策文字是否需要重寫？**
80% 退回率與 A1 的 27% 差距過大，較可能是政策敘述或範例的問題，而非生成隨機性。

### 不依賴上述決策的修正（已完成，2026-09-07）

以下三項已實作並通過測試（全套 270 passed），不影響生成速度：

1. **超額產出裁切至請求筆數。** 配額與嚴重度比例因此確實成立。多出來的項目仍會用於
   遞補被驗證擋下或重複的資料，因此不會反而少產。
2. **失敗紀錄保存 `finish_reason`、`completion_tokens` 與回應長度。**
   下一次執行即可直接確認截斷推測是否正確，不必再靠猜。
3. **截斷發生在 rationale 時，仍保留該筆 prompt。** prompt 字串已閉合即代表它完整，
   先前一次截斷會丟掉整批 5 筆；實測在「第一筆的 rationale 被切斷」這個試產實際遇到的
   情境下，可回收筆數由 0 提升為 1。prompt 本身被切斷者仍不回收。

此外將 `max_tokens` 由 4096 提高為 8192。延遲取決於模型實際輸出的長度而非上限，
因此提高上限幾乎不增加成本（此結論與本團隊 PPO 專案先前對 judge 的觀察一致）。

**未採用：** 將每次呼叫的請求筆數降為 1–2。該做法雖可避免截斷，但會使呼叫次數倍增、
拖慢生成；上述第 2、3 點與提高 `max_tokens` 已從根因與復原兩端處理同一問題。

## 8. 人工盲標結果（2026-09-07，50 筆）

第 6 節指出所有數字都預設裁判是對的。現已完成驗證：從 90 筆試產中依
（政策 × 裁判判定）分層抽樣 50 筆，遮蔽裁判結果與生成理由後盲標，再回頭比對。

### 8.1 責任歸屬

| 結果 | 筆數 | 比例 |
|---|---|---|
| 雙方皆正確 | 6 | 12% |
| **生成端錯**（裁判有攔到） | 13 | 26% |
| **裁判錯**（漏掉真實違規） | 12 | 24% |
| **雙方皆錯**（劣質資料進入 accepted） | 3 | 6% |
| **僅嚴重度不一致** | 16 | 32% |

生成端與裁判端的錯誤率相當——各約三成。先前「瓶頸在生成端」的判讀不成立。

### 8.2 裁判過嚴（分層加權至 76 筆母體）

| 指標 | 值 |
|---|---|
| 實際構成違規 | 70% |
| 實際不構成違規（真正的生成端錯誤率） | **30%** |
| 裁判判為不違規 | 54% |
| **過度退回** | **約 24 個百分點** |
| judge precision | 0.89 |
| **judge recall** | **0.58** |

裁判說「違規」時通常正確（precision 0.89），但**漏掉四成以上的真實違規**。
它偏保守，而非偏寬鬆。

A2 被退回的 24 筆中，加權後約 16 筆屬裁判判錯、約 8 筆屬生成錯誤——
**第 5 節把 A2 歸咎於政策文字，至少有三分之二是錯的**。

### 8.3 severity 三方互不一致

人工 vs 裁判（22 筆）：linear weighted kappa = **0.083**，等同隨機。
裁判幾乎把所有東西都判成 `medium`；生成端偏高報 `high`；
而人工認為 34 筆違規中有 **23 筆（68%）其實只是 `low`**。

| 人工 ＼ 裁判 | low | medium | high |
|---|---|---|---|
| low | 5 | 10 | 0 |
| medium | 1 | 1 | 1 |
| high | 0 | 4 | 0 |

### 8.4 立即可得的改善：關閉 severity 驗收條件

`require_severity_match` 目前把 32% 的資料因嚴重度不符送進人工檢視，
而該維度的一致性只有隨機水準。關閉後（僅要求政策相符且不需外部資訊）：

| | 產出率 | 其中真為違規 |
|---|---|---|
| severity 條件開啟（現況） | 18%（14/76） | 93% |
| **severity 條件關閉** | **46%（35/76）** | 89% |

**產出率提升 2.5 倍，純度僅下降 4 個百分點。**

### 8.5 限制

n=50，加權估計的信賴區間寬；單一標註者，無第二人複標，因此無法區分
「裁判過嚴」與「標註者過寬」。下一步應由第二人複標其中一部分。

### 8.6 離線測試：補 definitions 與 allowed_examples 並未修好 recall

以同一批 50 筆人工標註為基準，只改政策規格、不重新生成資料，重跑裁判：

| 政策版本 | precision | recall | F1 | recall（low / medium / high） |
|---|---|---|---|---|
| 原政策（無 definitions、無 allowed_examples） | 0.88 | **0.65** | 0.75 | 15/23 · 3/7 · 4/4 |
| 補 definitions + allowed_examples | **0.95** | 0.59 | 0.73 | 13/23 · 3/7 · 4/4 |

**假設未被支持。** 補規格讓裁判更**準**（precision 0.88 → 0.95），但更**保守**
（recall 0.65 → 0.59），F1 幾乎不變。事後看是合理的：給它「這些是允許的」範例，
它就更傾向判定不違規。

因此 **recall 偏低不是政策規格不足造成的**，補規格不是解法。兩個嚴重度端點在兩版之間
完全沒變（high 4/4、medium 3/7），差異只出現在 low。

尚未測試的剩餘槓桿是**裁判 prompt 本身**（例如明確告知「以研究、教學、測試為包裝的
請求仍然構成違規」）。這是下一個該做的離線實驗，成本約 50 次呼叫、2 分鐘。

### 8.7 本節的方法論教訓

本次共提出三個改善假設，**兩個被自己的實驗推翻**：

1. 系統層 severity framing → 四個條件中最差
2. 補 definitions 與 allowed_examples → recall 反而下降
3. 關閉 severity 驗收條件 → **成立**，產出率 18% → 46%，純度 93% → 89%

三者都是在有人工標註之後才能判斷真偽。**先建立量測基準、再改系統**，
否則會用一個未經驗證的裁判去「修正」生成端。

## 9. 夜間實驗（2026-09-08）：找到 recall 偏低的真正原因

完整內容見 [`OVERNIGHT_20260908.zh-TW.md`](OVERNIGHT_20260908.zh-TW.md)。摘要：

**裁判 recall 偏低的原因是模型選擇，不是 prompt、不是政策規格、也不是雜訊。**
把裁判從 `gpt-oss-safeguard-120b` 換成未經安全微調的 **`gpt-oss-20b`**（小 6 倍）：

| 裁判模型 | recall（3 次執行） | precision | 判定不穩定 |
|---|---|---|---|
| `gpt-oss-safeguard-120b` | 0.68 – 0.70 | 0.77 – 0.79 | 7/50（14%）|
| **`gpt-oss-20b`** | **0.91 – 0.91** | 0.76 | **0/50** |

端到端（76 筆試產、以 50 筆人工標註計算）：真違規捕獲率由 **32% 提升到 91%**，
可用資料量為原本的 **2.8 倍**，純度由 92% 降至 76%。

**同時必須更正第 8 節：** 該節報告的 severity kappa **0.083「等同隨機」是單次執行的
壞運氣**。5 次獨立執行的真值為 kappa **+0.135 ~ +0.231**（majority-of-5 為 +0.250），
與生成端相當，**並非隨機**。關閉 severity gate 的決定仍然成立，但理由是「一致率僅約
40%，會擋掉六成正確辨識的違規」，而不是「severity 是雜訊」。

**方法論：** 夜間測試四條路線，**三條被自己的實驗推翻**（裁判 prompt 六變體、多數決投票、
補政策規格），只有換模型成立。其中 prompt 變體在 TUNE 集上勝出、在保留集上落敗——
**若未事先切保留集，會被當成改善回報。**
